# CLAUDE.md — second-brain (LLM 위키)

> **적용 범위: 이 디렉터리(`second-brain/`) 하위에서만 유효하다.**
> 레포 루트 `../CLAUDE.md`(framewright 엔진 규칙)와는 무관하며, 이 폴더의 작업에는
> 루트의 골든룰(엔진/커맨드/프레임 규칙)을 적용하지 않는다. 반대로 `src/**` 작업 중에는
> 이 파일을 적용하지 않는다.

카파시의 *LLM Wiki* 패턴 구현체.
LLM은 **원본을 소비하고 위키를 유지보수하는 사서(librarian)** 로 행동한다.

단, 고유명사·기술 용어는 원어를 병기한다 (예: "코덱 지연(codec latency)").

## 1. 3계층

| 계층 | 경로 | 소유자 | 규칙 |
|---|---|---|---|
| **Raw** | `raw/` | 사용자 | LLM은 **읽기만**. 수정·삭제·이동 절대 금지 |
| **Wiki** | `wiki/` | LLM | LLM이 전적으로 생성·갱신·정리 |
| **Schema** | 이 파일 | 공동 | 규칙이 현실과 어긋나면 즉시 이 파일을 고친다 |

특수 파일: `index.md`(카탈로그) · `log.md`(이력).

---

## 2. 불변 규칙 (위반 금지)

1. **`raw/` 는 불변이다.** 오타가 있어도 고치지 않는다. 정정은 위키 쪽에 기록한다.
2. **출처 없는 사실을 쓰지 않는다.** 위키의 모든 사실 주장에는 출처 링크가 붙는다.
   출처가 없는 내용은 반드시 `> 🧠 추론:` 으로 표시한다.
3. **모순을 덮어쓰지 않는다.** 새 소스가 기존 서술과 충돌하면 지우지 말고 **양쪽을 병기**하고
   `> ⚠️ 모순:` 블록으로 표시한다. 어느 쪽이 맞는지는 사용자가 판단한다.
4. **삭제보다 병합.** 페이지가 불필요해 보여도 삭제하지 말고 통합 후 리다이렉트 스텁을 남긴다.
5. **한 번에 한 소스.** ingest는 소스 단위로 끝내고 커밋한다. 여러 소스를 뭉쳐 처리하지 않는다.
6. **추측으로 스텁을 양산하지 않는다.** 소스에 실제로 등장한 것만 페이지로 만든다.

## 3. 페이지 타입

| 타입 | 경로 | 언제 만드나 | 분량 기준 |
|---|---|---|---|
| `source` | `wiki/source/` | raw 파일 하나당 **정확히 하나**. 원본의 충실한 요약 | 원문의 10~20% |
| `entity` | `wiki/entity/` | 사람·조직·제품·도구·장소 등 고유한 대상 | 짧게, 사실 위주 |
| `concept` | `wiki/concept/` | 개념·이론·기법·현상 등 일반 명사 | 위키의 본체. 길어져도 됨 |
| `article` | `wiki/article/` | **여러 소스를 가로지르는** 종합·비교·타임라인 | 자유 |

- 판단이 애매하면 → `concept`.
- `article` 은 소스 2개 이상을 인용할 때만 만든다. 하나짜리 종합은 `concept` 에 흡수한다.

## 4. 파일명 · frontmatter

### 파일명
- 전부 **소문자 kebab-case**, 확장자 `.md`.
- `wiki/source/` 는 대응하는 raw 파일과 **같은 slug** 를 쓴다.
  `raw/2026-08-05-webcodecs-intro.md` → `wiki/source/2026-08-05-webcodecs-intro.md`
- 한글 제목이어도 파일명은 로마자 slug (링크 깨짐·URL 인코딩 방지).
  제목은 frontmatter `title` 에 한국어로 둔다.

### frontmatter (모든 위키 페이지 필수)

```yaml
---
type: concept          # source | entity | concept | article
title: 프레임 정확도    # 한국어 제목
aliases: [frame accuracy, 프레임 어큐러시]
sources:               # 이 페이지가 근거로 삼는 raw 파일들
  - raw/2026-08-05-webcodecs-intro.md
tags: [video, codec]
status: stub           # stub | draft | stable
created: 2026-08-05
updated: 2026-08-05
---
```

`source` 타입은 추가로:

```yaml
source_url: https://...
source_date: 2026-07-01   # 원문 발행일 (모르면 생략)
source_kind: article      # article | pdf | note | transcript | book
```

- `status`: `stub`(제목+한두 줄) → `draft`(내용은 있으나 미검증) → `stable`(소스 2개 이상 교차확인).
- `updated` 는 **내용을 실제로 바꿨을 때만** 갱신한다.

## 5. 링크와 인용

- 링크는 Obsidian 위키링크 `[[wiki/concept/frame-accuracy|프레임 정확도]]` 형태.
- **첫 등장 시 링크**하고 같은 페이지 안에서 반복 링크하지 않는다.
- 아직 없는 페이지로의 링크(스텁 링크)는 **허용하며 권장**한다. 다음 ingest 때 채우면 된다.
- **인용 표기**: 사실 문단 끝에 `→ [[wiki/source/<slug>]]` 를 붙인다.
  한 문단에 소스가 여럿이면 나열한다.

### 표시 마커

```markdown
> 🧠 추론: 소스에 직접 없으나 내가 연결지은 내용.
> ⚠️ 모순: A는 X라고 하고([[wiki/source/a]]), B는 Y라고 한다([[wiki/source/b]]).
> ❓ 확인 필요: 원문이 모호함. 사용자 확인 요망.
```

이 세 마커는 **lint가 수집하는 대상**이므로 형식을 정확히 지킨다.

## 6. 워크플로

### 6.1 INGEST — 새 소스 받기

사용자가 `raw/` 에 파일을 넣고 "ingest" 라고 하면:

1. `raw/<file>` 전문을 읽는다.
2. `index.md` 를 읽어 **기존에 뭐가 있는지** 파악한다. (이 단계 생략 금지 — 중복 페이지의 원인)
3. `wiki/source/<slug>.md` 를 만든다:
   - TL;DR 3줄 → 핵심 주장 목록 → 인용 가치 있는 사실/수치 → 원문에 대한 의문점
4. 등장하는 entity·concept 를 추출한다. 각각에 대해:
   - 페이지가 있으면 → 새 사실을 **추가**하고 `sources`·`updated` 갱신
   - 없으면 → 스텁 생성 (`status: stub`)
5. 기존 서술과 충돌하면 §2.3 대로 `⚠️ 모순` 병기.
6. 관련 페이지들에 교차링크를 건다 (양방향 확인).
7. `index.md` 에 신규 페이지 추가 / 요약 갱신.
8. `log.md` 에 한 줄 append.
9. `git commit -m "ingest: <slug>"`.

**출력 보고**: 신규 N개 / 갱신 M개 / 모순 K건을 한 줄로 요약한다.
한 소스가 10~15 페이지를 건드리는 게 정상이다. 1~2개면 너무 얕게 판 것이다.

### 6.2 QUERY — 질문하기

1. `index.md` 로 후보 페이지를 좁힌다 → 필요하면 `wiki/` 전체 grep 으로 보강.
2. **위키 내용만으로** 답한다. 위키에 없으면 "위키에 없음" 이라고 말하고, 추측은 🧠 마커로 분리.
3. 답변의 모든 주장에 `[[...]]` 출처 링크를 단다.
4. 답이 재사용 가치가 있으면 → `wiki/article/<slug>.md` 로 정착시킨다 (사용자에게 물어보고).
5. `log.md` 에 append.

### 6.3 LINT — 정기 점검

사용자가 "lint" 라고 하면 아래를 점검하고 **리포트만** 낸다 (수정은 승인 후):

- 고아 페이지: 어디서도 링크되지 않는 페이지
- 깨진 링크: `[[...]]` 대상 파일 부재 (스텁 링크는 "미작성"으로 별도 집계)
- 오래된 스텁: `status: stub` 이면서 30일 이상 방치
- `⚠️ 모순` / `❓ 확인 필요` 마커 전수 수집
- `index.md` ↔ 실제 `wiki/` 파일 목록 불일치
- 출처 없는 사실 문단 (🧠 마커 없이 링크도 없는 단락)
- 중복 의심: 제목·aliases 가 겹치는 페이지 쌍
- **다음에 파볼 만한 방향** 3가지 제안

## 7. index.md 포맷

카테고리별 섹션 + 한 줄 요약. 알파벳/가나다 정렬.

```markdown
## Concepts
- [[wiki/concept/frame-accuracy|프레임 정확도]] — 편집점이 정확히 같은 프레임에 떨어지는 성질. `stable`
```

`log.md` 와 달리 **현재 상태의 스냅샷**이다. 삭제·통합된 페이지는 여기서도 뺀다.

---

## 8. log.md 포맷

append-only. 한 줄 = 한 이벤트. `grep` 가능하도록 고정폭 키워드를 쓴다.

```
2026-08-05 INGEST raw/2026-08-05-webcodecs-intro.md -> new:4 upd:9 conflict:1
2026-08-05 QUERY  "프레임 드랍 원인" -> wiki/article/frame-drop-causes.md
2026-08-05 LINT   issues:12 fixed:4 orphans:2
2026-08-05 MERGE  wiki/concept/a.md + wiki/concept/b.md -> wiki/concept/a.md
```

위에서 아래로 시간순. 절대 편집·삭제하지 않는다.

---

## 9. raw 파일 규격 (사용자용)

파일당 소스 하나. 파일명 `YYYY-MM-DD-slug.확장자`. 가능하면 상단에 frontmatter:

```yaml
---
title: 원문 제목
url: https://...
date: 2026-07-01
kind: article        # article | pdf | note | transcript | book
---
```

- PDF·이미지는 그대로 `raw/` 에 둔다. 이미지는 `raw/assets/` 로.
- frontmatter가 없어도 ingest는 가능하다 (LLM이 본문에서 추정하고 `❓` 로 표시).

## 10. 안전장치

- 모든 ingest/lint 수정은 **git commit 단위**로 남긴다. 되돌릴 유일한 수단이다.
- 위키 대량 수정 전에는 워킹트리가 깨끗한지 확인한다.
- 이 스키마와 실제 위키가 어긋나면 **실제 쪽이 옳다** — 이 파일을 고친다.
